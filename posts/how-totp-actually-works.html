Six digits, thirty seconds: how TOTP actually works

The rotating codes in your authenticator app look like magic and are actually about fifteen lines of code. Here's the whole mechanism, and the threat model it quietly assumes.

When you scan a QR code to set up two-factor authentication, exactly one interesting thing happens: the service hands your phone a shared secret. The QR code is just a URI — 

otpauth://totp/GitHub:alice?secret=JBSWY3DPEHPK3PXP&issuer=GitHub

— and the secret parameter is a random key, base32-encoded so it survives being typed by hand. From that moment, your phone and the server both know the key, and neither ever sends it anywhere again. Every code you'll ever type is derived from it, plus one other input: the time.

The algorithm, whole

TOTP (RFC 6238) is a thin wrapper over HOTP (RFC 4226). HOTP computes a code from a key and a counter; TOTP just defines the counter as "how many 30-second windows have elapsed since the Unix epoch": 

counter = floor(unix_time / 30)

code = HOTP(key, counter)
     = truncate(HMAC_SHA1(key, counter_as_8_bytes)) mod 10^6

The HMAC gives you 20 pseudorandom bytes. Then comes my favorite step in any widely-deployed standard, dynamic truncation: take the low four bits of the last byte, use them as an offset into the digest, read four bytes from that offset, mask off the sign bit, take the result mod 1,000,000, left-pad with zeros. 

offset = digest[19] & 0x0f
value  = (digest[offset]   & 0x7f) << 24
       | digest[offset+1] << 16
       | digest[offset+2] << 8
       | digest[offset+3]
code   = (value % 1_000_000).toString().padStart(6, "0")

Why the offset dance instead of just reading the first four bytes? The RFC's authors wanted the extracted bits to depend on the digest itself, so no fixed position could develop a bias. It's a small paranoia, cheaply bought — very much the house style of good security engineering.

That's the entire protocol. No network round-trip, no per-login state, no clock synchronization protocol — the server simply computes the same function and compares, usually accepting a window of ±1 step to absorb clock drift. Both sides agreeing on the time is the synchronization.

What this design buys you

  • Offline generation. The phone needs no connectivity. Codes work in airplane mode, in a basement, on a device that has never touched your accounts.
  • No secret on the wire at login. You type a derivative of the key, valid for seconds. A leaked code from last Tuesday is worthless.
  • Radical implementability. SHA-1, HMAC, and integer math. It runs on a smart card, a microcontroller, a 2008 feature phone. That's why it won.

What it quietly assumes

TOTP's threat model is narrower than its reputation. The design defends against a replayed or stolen password. It does not defend against:

  • Phishing in real time. A fake login page can ask for your code and relay it to the real site inside the 30-second window. Modern phishing kits do this automatically. The code proves you have the key — it doesn't prove you're talking to the right party. (That gap is exactly what WebAuthn closes.)
  • Secret exfiltration. The shared secret sits in a database row on the server and in storage on your phone, forever. Either end can leak it, and a leaked TOTP secret is a skeleton key — it generates valid codes for eternity, silently. Where that secret physically lives — app sandbox, keychain, hardware-backed keystore — is the whole ballgame.
  • The enrollment moment. The QR code is the secret, in plaintext, on your screen. Screenshot it, sync that screenshot to a cloud photo library, and your "second factor" now has as many copies as your camera roll.

None of this makes TOTP bad. It makes it a possession factor with an asterisk: you're proving possession of a copyable number, not of a device. The distinction is invisible right up until it's the entire story of how an account got taken over.

The device-layer footnote

Notice what the strongest deployments all do: they shrink the number of places the secret exists and make those places hard to read. Hardware-backed keystores. Secrets flagged non-exportable, excluded from backups. HSMs on the server side. The algorithm was never the weak point — fifteen lines of arithmetic rarely are. The storage is. In security, the interesting question is almost never what's computed; it's where the key sleeps at night.
