Phishing-proof by construction: what WebAuthn gets right

Every credential you can type is a credential you can be talked out of. WebAuthn's quiet radicalism is refusing to give you anything to surrender.

Phishing works because humans authenticate the wrong thing. We look at a page that resembles our bank and hand it a secret that works at our bank. Every typeable credential — password, SMS code, TOTP digits — inherits this flaw, because the human is the component deciding where the secret goes, and humans verify pixels, not origins.

Decades of countermeasures have tried to upgrade the human: security awareness training, padlock icons, EV certificates, "check the URL carefully." The results are in, and they're humbling. WebAuthn takes the opposite approach: remove the human-transferable secret from the protocol entirely.

The mechanism

When you register a passkey or security key, the authenticator generates a fresh asymmetric key pair for that site specifically. The site stores the public key. The private key stays in the authenticator — a phone's secure element, a USB key, a TPM — and is marked non-exportable. There is no shared secret. There is nothing to remember, and therefore nothing to type, and therefore nothing to type into the wrong place.

Login is a challenge–response:

server  → browser: random challenge
browser → authenticator: { challenge, origin: "https://bank.example" }
authenticator: sign(private_key[origin], challenge ‖ origin ‖ flags)
server: verify with stored public key — including the origin

Two details in that flow do all the security work:

  • The browser supplies the origin, not the user. The signed message includes the actual domain the request came from, as observed by the browser. On bank-example.phish.co, the signature says so, and verification at the real bank fails. The user's opinion of which site they're on is no longer part of the protocol.
  • Keys are per-origin. The authenticator scopes every key pair to the domain that registered it. The phishing site can't even request the bank's credential — from the authenticator's perspective, it's a different application asking for a key that doesn't exist. As a side effect, credentials can't be correlated across sites; there's no username-equivalent to leak.

The adversary's new job

Against TOTP, a phisher's job is to build a convincing page and relay six digits within thirty seconds — automatable, scalable, cheap. Against WebAuthn, the same attacker must either break the cryptography, compromise the victim's browser or OS, or physically obtain the authenticator and its local unlock. The attack didn't get harder. It changed category — from "send a convincing email" to "be present." Security wins that change an attacker's category are rare, and worth noticing when they happen.

The honest caveats

  • Account recovery is the new perimeter. If a phisher can't steal the credential, they'll phone support and cry. Every WebAuthn deployment is exactly as strong as its weakest fallback path — which is often "email a reset link," quietly demoting the whole system back to password-grade.
  • Synced passkeys trade device-binding for usability. When the private key syncs through a cloud account, possession of your cloud login starts to imply possession of your keys. Reasonable trade, honestly made — but it moves the load-bearing wall, and you should know which wall is load-bearing.
  • The signature travels through the machine you're using. A compromised endpoint can't steal the key, but it can ask it to sign things. Malware in the session is still malware in the session.

The design lesson

The deep pattern here shows up everywhere good security engineering does: don't train users to make a distinction — make the distinction structurally impossible to get wrong. WebAuthn didn't teach anyone to read URLs. It made the URL a cryptographic input, checked by machines, every time, without asking. The best security controls are the ones with no user-shaped hole in the middle.
